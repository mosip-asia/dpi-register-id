# D1 — Timeouts, bounded retry, and a UIN that survives a failed step

## Previous

IDRepo and Keycloak calls used fixed timeouts of a few seconds and did not retry. A lost response dropped the UIN that had just been allocated. A down backend was not distinguished with `Retry-After`.

## Expected

Idempotent calls use configurable timeouts and bounded backoff. When a backend is down, return HTTP 503 with `Retry-After`. An allocated UIN survives a later step failing. UIN generation must not be retried, because a lost 200 would burn another UIN.

## Now

`MOSIP_HTTP_TIMEOUT` (default 10s), `MOSIP_HTTP_RETRIES` (default 2 extra attempts), and `MOSIP_HTTP_BACKOFF_SECONDS` (default 0.2s, doubled, cap 5s) drive IDRepo `_send`, the IDRepo token request, identity reads, the demographic exchange, the health probe, Keycloak admin calls, and the OIDC code exchange. Non-idempotent POSTs run once. `generate_uin` passes `retries=0`. Connection loss and HTTP 502/503/504 become status 503. Enrol and a lost Keycloak credential call return 503 with `Retry-After: 30`. `_allocate` writes the UIN and registration id onto the ticket before the identity write, so a later failure keeps them.

## What was done

The fixed `timeout=2`, `timeout=3`, `timeout=5`, and `timeout=10` literals on live MOSIP and Keycloak HTTP calls were replaced with `_http_timeout()`. Keycloak idempotent GETs use the shared retry helper. Credential provisioning marks a connection loss as retryable, and the API maps that to 503. The 409 path still does not reset a password.
