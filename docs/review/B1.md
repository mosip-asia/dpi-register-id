# B1 — Password setup is bound to the enrolment

## Previous

`POST /api/credentials` was unauthenticated. Knowing a UIN was enough to reset that Keycloak user's password. A 409 from user creation looked the user up and called `reset-password` when the UIN attribute matched.

## Expected

Setting a password is bound to the enrolment that created that UIN, or to a verified email link. Do not reset a Keycloak user identified only by UIN.

## Now

Enrol returns a single-use `credentialTicket` after the server allocates the UIN. `POST /api/credentials` requires that ticket, and the ticket UIN must match the body. A bad ticket is 401 and Keycloak is not called. A Keycloak 409 returns HTTP 409 with "An account for this UIN already exists." and does not look the user up or reset the password. There is no verified-email path; the ticket is the binding.

## What was done

`take_credential` checks the token, the UIN, and single use. `provision_citizen` returns `account already exists` on 409. The credentials handler maps that detail to HTTP 409. The test that used to expect a reset now fails if `reset-password` is called.
