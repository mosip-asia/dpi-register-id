# A3 — Server-allocated UIN

## Previous

The browser called `GET /api/idgenerator/uin`, then submitted any UIN it wanted on enrol. When the generator failed and the mock fallback was on, the client invented a 10-digit number. An empty generator URL was sent to the IDRepo host.

## Expected

`POST /api/enroll` allocates the UIN from the kernel idgenerator at `http://idgenerator.kernel`. A client-supplied UIN is rejected. A failed generator does not invent a number. A missing service token fails the generator call on the shipped path.

## Now

`EnrollRequest` rejects a body `uin`. There is no public `GET /api/idgenerator/uin`. With the fallback off, an empty `MOSIP_IDGENERATOR_BASE_URL` calls `http://idgenerator.kernel/v1/idgenerator/uin`, a missing authmanager cookie fails before that call, and a failed response returns an empty UIN with status 503. Helm sets `idgeneratorBaseUrl` to `http://idgenerator.kernel`. The lab page fills the UIN from the enrol response and does not post one. Local fallback may still use the in-process generator when the URL is empty.

## What was done

`generate_uin` and `_idgenerator_base` implement that split. `random.randint` in this client is only the registration-id suffix, not a UIN. The lab template stopped calling the removed route. Tests cover the kernel URL, the missing-token failure, and the rejected client UIN.
