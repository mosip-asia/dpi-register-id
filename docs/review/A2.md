# A2 — IDRepo service token

## Previous

IDRepo calls already cached an authmanager `clientidsecretkey` token and sent it as `Cookie: Authorization=<token>`. The empty `MOSIP_APP_ID` fallback was `resident`. The review text asked for a Keycloak `client_credentials` token, the same pattern as the Kit eSignet journey.

## Expected

The PDF asked for a Keycloak `client_credentials` token carrying `REGISTRATION_PROCESSOR` or `ID_REPOSITORY`. MOSIP kernel IDRepo does not accept that token. The authmanager cookie is the call that IDRepo is built for. The client id for that cookie is `mosip-regproc-client` with `appId` `regproc`.

## Now

IDRepo still authenticates with authmanager `POST /v1/authmanager/authenticate/clientidsecretkey` and `Cookie: Authorization=<token>`. An empty `MOSIP_APP_ID` falls back to `regproc`. Helm and `.env.example` set `regproc`. A comment on the token request records that this cookie is not a Keycloak access token. Keycloak `client_credentials` remains the admin API only.

## What was done

The appId fallback in `IDRepoClient._mosip_token` changed from `resident` to `regproc`. The token URL, cookie header, and cache were left on authmanager. The Keycloak wording in the review is an accepted exception: the Kit eSignet token is a different audience from kernel IDRepo.
