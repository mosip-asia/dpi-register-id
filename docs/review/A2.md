# A2 — IDRepo service token

## Previous

IDRepo calls cached an authmanager `clientidsecretkey` token and sent it as `Cookie: Authorization=<token>`. The Kit asked for a Keycloak `client_credentials` token, the same pattern as the eSignet journey.

## Expected

The token is a Keycloak `client_credentials` access token from `KEYCLOAK_INTERNAL_URL` and `KEYCLOAK_REALM`, using `IDREPO_CLIENT_ID` and `IDREPO_CLIENT_SECRET` with no defaults. It is cached until `expires_in` minus 30 seconds and sent as `Cookie: Authorization=<token>`.

## Now

`IDRepoClient._mosip_token` posts form data (`grant_type`, `client_id`, `client_secret`) to `{KEYCLOAK_INTERNAL_URL}/realms/{KEYCLOAK_REALM}/protocol/openid-connect/token` and reads `access_token`. The cookie header is unchanged. `MOSIP_AUTHMANAGER_URL`, `MOSIP_SECRET_KEY`, and `MOSIP_APP_ID` are gone. Helm sets `keycloak.idrepoClientId` and reads `IDREPO_CLIENT_SECRET` from `existingSecret`.

## What was done

The authmanager client-id secret call was replaced with the Keycloak token request. Readiness, Compose, and the chart follow `IDREPO_CLIENT_ID` and `IDREPO_CLIENT_SECRET`.
